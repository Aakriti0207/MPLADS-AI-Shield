# district_centroids.csv -- source & caveats

## What this file is

An approximate **geographic centroid for each Indian district**
(latitude/longitude of roughly the middle of the district), used as a
**fallback** for the Map feature because no MPLADS data source in this
repository contains a real, project-level coordinate (see
`app/geo_centroids.py`'s module docstring for the full investigation).

It is NOT project-level location data. Every project in the same
district is plotted at the *same* point.

## Source

Fetched from the public GitHub repository:

    https://github.com/JeetKaria06/India-District-Wise-Corona-Cases
    file: district-wise-centroids.csv (726 rows)

Per that repository's own README, the coordinates were generated by
geocoding each district's name through the **OpenStreetMap Nominatim
API** (openstreetmap.org's open geocoding service) -- i.e. they are
"where is this district on the map" lookups, not survey-grade
centroids and not derived from any MPLADS or government source.

Retrieved: 2026-09-19, via `raw.githubusercontent.com`. Columns were
renamed to lowercase (`state, district, latitude, longitude`) and
values rounded to 6 decimal places (~11cm nominal resolution, matching
this project's own `Project.latitude`/`Project.longitude` DB column
precision in `app/models.py` -- the rounding does not imply that level
of real accuracy, it only avoids carrying meaningless extra digits).
No rows were removed, added, or hand-edited.

## How it's used

`app/geo_centroids.py` loads this file once per process and resolves
a project's approximate location in two steps:

1. **District centroid** -- if the project's (state, district), after
   normalization, matches a row in this file.
2. **State centroid** -- if the district doesn't match (e.g. a newer
   district created after this file was generated, or a spelling
   difference this project's normalization doesn't bridge), fall back
   to the **mean of that state's own matched district centroids**,
   computed at load time from this same file -- not a separately
   sourced number.

If even the state can't be resolved, no coordinates are returned.
Every project response reports which of these happened via
`location_precision` (`"district_centroid"` / `"state_centroid"` /
`null`), so nothing downstream can mistake this for a real address.

## Coverage against this project's canonical dataset

Checked against `data/processed/canonical_projects.csv` (43,863
projects, 35 states, 735 distinct district values) at the time this
file was added:

- 35/35 states resolve (state-level fallback always available).
- ~83% of project *rows* resolve to a district-level centroid on an
  exact normalized-name match. The rest fall back to their state's
  centroid. Unmatched districts are mostly districts created/renamed
  after this reference file was generated (e.g. Telangana's
  post-2016 districts) or spelling variants (e.g. "Mahesana" vs.
  "Mehsana") -- deliberately NOT bridged with fuzzy matching, because
  a wrong exact-sounding match would be a fabricated, misleading
  project-specific coordinate, which is worse than the honest,
  coarser state-level fallback.
